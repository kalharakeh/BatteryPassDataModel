# DPP V3 Compliance Rebuild — Key Decisions

Decided by the product owner on 28 Oct 2026, after the comparison of the V3 attribute list with the app.

## Context

- **Goal:** cover every row of `DPP_V3_vs_App_comparison_2026-10-28_v2.xlsx` and comply with `DPP_Internal_2026_BatteryPass-Ready_DataAttributeLongList_v2.0_August version_V3.xlsx` (73 attributes, tab "Data attribute longlist_v2.0").
- **Freedom:** the passport app has no real users or data yet, so data can be reset and the model restructured; changes can be bundled freely.
- **Baseline:** branch `security/demo-api-hardening`, commit `8c8bfe7`, ASP.NET app in `web/`; 464 tests passing.

## Role rule

Where the file says "the person who has legally purchased the battery (or a third party on their behalf)", it means **the members of the cluster the battery belongs to**: cluster users **see** that data, cluster admins **edit** it.

Confirmed: market surveillance also sees purchaser data, because every purchaser row in the file lists it (decision 12). Shared legitimate-interest data (#43, #45–48) is seen by the cluster but maintained by Scania's team (decision 10).

## Decisions

| # | Topic | Decision | What it means for the build |
|---|---|---|---|
| 1 | Data model | Rebuild on the BatteryPass-Ready **v2.0** data model; reset batteries, passports and family templates; keep users, clusters and API tokens | Replace the v1.2 aspect models, their sample payloads and the demo fallbacks. Validate against the v2.0 JSON schema (repository linked from the file's Technical references tab). |
| 2 | Catalogue | The 73 V3 attributes become the app's **single attribute catalogue** | One entry per attribute: v2.0 technical name, level, audience, editor, static/dynamic and update rule, unit, format, requirement for Other industrial, mandatory from Feb 2027. Storage, pages, forms, access checks, APIs, validation and a compliance test read from it. Anything not in it is removed, except app mechanics (clusters, users, signatures/trust, audit). |
| 3 | Levels | Family → model → **batch** (model × calendar year × manufacturing site) → battery, plus **manufacturing-site** data | The batch holds carbon footprint, recycled and renewable content, DoC, test reports and the model identifier (16 rows). The site holds manufacturer identifier and information and the manufacturing place (#12, #15, #16). |
| 4 | Category | All products are **Other industrial >2 kWh** | V3 covers everything; the 19 rows removed in V3 stay out. Conditional rows still apply (#19, #24, #49–52, and the non-cycling exemptions on #71, #72, #74, #82–85). |
| 5 | Identifiers | Choose the EN 18219 / ISO/IEC 15459 scheme **later** | Build a configurable ID format with clearly marked test IDs; choose the scheme and register with its issuing agency before go-live. |
| 6 | Legitimate-interest roles | **Split into three** roles | Repair/repurposing/remanufacturing operators: #43, #45, #46, #47, #48. Recyclers and battery treatment operators: #43, #45, #48. Authorised treatment and WEEE facilities: #48. |
| 7 | Documents | Public documents as **links** to the company website; restricted documents **uploaded** to the app | Links are stored with content type, language and title (v2.0 keys); uploads are served only to the attribute's audience. |
| 8 | Live data | **BMS feed** through the external API, **manual entry** by cluster admins, and a **JSON upload tool** | The upload takes per-battery static parameters or live data. Only catalogue attributes are accepted, each only if the uploader may edit it; other keys are reported and ignored. The existing BMS export format (e.g. `battery-passport_VPC8C05-6788_….json`) should map in: state of charge, equivalent cycles and temperature (mapping: decision 17). Proposed: static per-battery parameters by Scania's team, live data by Scania's team and the battery's cluster admins. |
| 9 | Cluster admins' rights (workbook D-09) | Purchaser data, **plus handing their batteries over** to another cluster | Cluster admins edit only purchaser data and can transfer one of their batteries to another cluster (e.g. after a resale), through a transfer step so it doesn't simply vanish from their view. Battery model/batch and manufacturing site stay with Scania's team. Software version is removed (not in the file). Design proposal: the cluster is not passport data, so a transfer doesn't need a new passport. |
| 10 | Shared legitimate-interest data (workbook D-35) | **Scania's team** edits; the battery's cluster only sees it | Kept once per battery model in the family/model template (#43, #45–48), as the file defines them per model. |
| 11 | Fades and expected lifetime (workbook D-43) | Template value at placement on market; **Scania's team and the battery's cluster admins** re-state them for that battery when its status changes | Needs per-battery values for #59, #69, #74, #79 and #81 that override the template, enterable by hand or by JSON upload. |
| 12 | Market surveillance | Sees purchaser data, **as the file requires** | Confirms the access matrix: battery's cluster + market surveillance (+ Scania's team) for the 10 purchaser rows. |
| 13 | Repurpose / remanufacture / re-use | When the status becomes Repurposed, Remanufactured or Reused, a **new passport linked to the previous one** is issued and the previous passport becomes **"inactive"**; the economic operator responsible for the new passport is recorded (#7) | Follows #22 ("a new battery passport must be issued … when placed on the market again") and #2 (DPP status "inactive"). Waste is an ordinary new version; the passport is later "marked-for-deletion" after recycling or export. Refined by decision 19: the new passport comes when the battery is placed on the market again; a repair sets "re-used" on the same passport. |
| 14 | Battery transfer | The **receiving cluster accepts** before the transfer takes effect; afterwards the **previous cluster no longer sees** the battery's purchaser data | The file grants purchaser data to the current purchaser only. |
| 15 | Status change and fades | The status change (form or JSON upload) **also asks for the re-stated fades and expected lifetime** | Keeps #59, #69, #74, #79 and #81 in step with #22. |
| 16 | Passport level | **One passport per pack** (e.g. `VPC8C05-6788`); a system (e.g. `SYSTEM-001`) is only a grouping | The battery record is the pack. System and module identifiers in uploads are not stored (not in the file). |
| 17 | BMS export mapping (design O-2) | #83 from **`equivalentChargeAndDischargeCycles`**; #87 from the **latest measured pack temperature** | The export team is asked to fill state of charge, cycles and production date; confirm the cycle count (partial cycles added up, one full charge plus one full discharge = one cycle); add one pack-temperature field in °C and say which sensors it uses; give measurement times; and drop the IP address, CAN payload and exporter details. Remaining capacity is optional (it suggests #59). |
| 18 | Manufacturing date #17 (design O-3) | **Year and month** (YYYY-MM), as the file and the regulation say | The schema's format is a full date; format checks are annotations by default, so validation passes. Tell BatteryPass-Ready about the mismatch. |
| 19 | Repairs (design O-4) | Follow the file's DIN note: a repair is recorded as **"repaired" under status "re-used"** on the same passport, with a repair history; a **new passport only when the battery is placed on the market again** | Recorded by Scania's team or the battery's cluster admins through the status change (re-stated values asked as usual) and shown with the status to the same readers. The history isn't in the passport JSON (no schema field). Refines decision 13. |
| 20 | Battery picture (design O-5) | **Keep one picture per battery family**, set by Scania's team | Shown on the public summary. Not passport data and not in the JSON; cluster admins can no longer change it. |
| 21 | Schema copies (design O-6) | **Copy both v2.0.1 Other industrial schema files** into the repository in step 1 | `Other_Industrial_Above_2kWh_2.0.1.json` and `Other_Industrial_Above_2kWh_Feb27_2.0.1.json`, with a note giving the source address, the date, the CC BY 4.0 licence and © BatteryPass-Ready Consortium. Tests run offline. |
| 22 | Test packages | **JsonSchema.Net** checks values and passports against the official schemas (step 1); **EphemeralMongo** runs the repositories' tests against a throwaway MongoDB (from step 2, where the database code arrives) | EphemeralMongo starts a temporary mongod inside the test run; no Docker or local install. Its first run downloads a mongod binary (about 100 MB). |
| 23 | Team pages (step 2d) | **Reuse today's admin page layout**, styles and shared page parts; no new layout options | The family page, Edit battery, Conformance, Revision history and the batteries list keep their look with the new data underneath. Only screens with no counterpart today get a mock-up (batch page, sites and operators, republish question, restricted documents). The new pages replace the old ones in place under the existing menu entries; no temporary menus, preview entries or duplicates in the version being built. |
| 24 | Removing a value (step 2d) | The team's editors **may remove a value** by emptying its field; uploads and feeds keep "empty never overwrites" | A value a published passport needs by February 2027 can't be removed (change it instead). Removals are audited with the value they replaced and republish like changes. |
| 25 | Removing records (step 2d) | Families, models, batches, sites and operators **can be removed while nothing uses them** | Once a record has models, batches, batteries or passports, the page says why it stays. Removing deletes its values and uploaded documents, and is audited. The old family page could remove a model. |
| 26 | New model from a copy (step 2d) | Adding a model offers **"Start from: empty or a copy of a model"**, from any family | Copies the typed values, marked as entered by the team member at that moment; uploaded documents and batches aren't copied. The old family page had "Base on existing template". |
| 27 | Look of the team pages (step 2d) | Today's palette, fonts, cards, buttons and inputs, with a **calmer finish**: one card per thing, outlined sentence-case tags, orange only for "missing", green only for "done", thin progress bars, slim message lines, one heading scale, gentle motion | Amends decision 23. The team pages look a little more refined than the other admin tabs, which can get the same finish when step 3 rebuilds them. The shared `site.css` is not changed. |
| 28 | Extreme-temperature times (Polarion STD-800, "Dynamic attributes agreed L0") | **Add four live values beyond the file, E1–E4**, as the Polarion list says: time spent in extreme temperatures above and below the boundary, and time spent charging during extreme temperatures above and below (DIN DKE 99100, 6.7.7.5–6.7.7.8). DIN DKE requires them for Other industrial; Polarion marks them "BMS implements" | The BMS's own boundaries define "extreme", so the app needs no thresholds. Taken from the BMS export's `timeSpentInExtremeHighTemperature`, `timeSpentInExtremeLowTemperature` and `timeSpentChargingInExtremeTemperature` (seconds, converted to whole minutes as amended below); the one charging field fills both E3 and E4, since Polarion says charging in extreme temperatures is prevented and always zero. Not in the V3 file or BatteryPass-Ready v2.0.1: the schema allows extra fields, so passports still validate, but other readers won't know them. Seen like #87 (the battery's cluster and market surveillance). They never block publication. Deep-discharge events (6.7.8.2, optional for Other industrial) stay out. |
| 29 | External API (step 3c) | **Keep it**, rebuilt on the new model and the new access rules | It keeps doing what it did: clusters, a cluster's batteries, a battery's passport, its sections and values, creating batteries, publication, the live values (#63, #83, #87, E1–E4) in place of telemetry, and their history in place of the telemetry history, read from the change log. Each answer is cut by the one visibility rule (`AudienceRules`, design 5), so a change to who sees what changes the API too; cluster tokens write only the live values (J-10). The endpoints whose data isn't in the file go: operations (location of use, contact person, active), the battery-model label and the software version (decisions 2 and 9; Appendix C, X-03, X-05, X-22 to X-24). Amends design 8.4. The bulk upload endpoint stays in step 5. |
| 30 | Review of the rebuild against the V3 file, the comparison and the old app (29 Oct 2026) | **Keep building as designed**, and restore or add what the review found useful | Restored or added: the **Registry** rebuilt on the new model as a read-only list of the batteries each signed-in reader may open (team and authorities: all published; a cluster's users and admins: their cluster's; the legitimate-interest roles: all published), which also replaces the cluster admins' old "Managed passports" list until step 4; links from the team's battery page to its summary, detail page, QR code and audit entries; clickable versions with their signature details; a QR code for drafts, team only; the live-value history on the detail page, for those who may see the live values; each conditional attribute's own condition shown in the editors; admins can delete an account; a "Not allowed" page instead of the access-denied redirect loop. Confirmed as decided: the telemetry charts, the old trust tab, the page listing a battery's passports and the per-passport audit page stay removed; `/api/passports` stays read-only; conditional values can be removed even from published passports (decision 24 applies to values needed by February 2027); the family name stays on the public summary (X-02). Tidied: plain words for where a value came from, the help pages lose the old validate/sign workflow now, and the cluster admins' token form loses the options that no longer do anything. |
| 31 | Module data (X-08, restored) | **Each battery keeps its module list**: position, serial number and connectivity ID per module, from the battery system's JSON export (`metadata.identifiers.deviceIdentifiers.childrenIdentifiers`) or typed by the team. The count is the number of modules. **A description** is typed once per battery model | Not V3 data and not in the passport JSON: app data, like the family picture. The module count and the model's description show on the public summary; the module IDs only to the team, the battery's cluster and market surveillance. The team edits them until step 5's BMS adapter fills them from the export. The export's parent system identifiers are kept in mind but not used. |
| 32 | Demo data (after the reset of 3d-2) | **A demo data set the team can reset or clear**, like the old app's demo button, on the new model | One "Demo data" card on the team's admin pages: **Reset demo data** removes the demo records and seeds them again; **Clear demo data** removes them and keeps the real data. Both ask first and are logged. The seed shows the app's features: family Compact with models Compact 7M and Compact 13M, and family Core with model Core (values from the old templates mapped to the V3 attributes; the three old pictures, back from the tag `app-v1.2-before-dpp-v3`, as family pictures; TEST- identifiers); a few sites, operators and batches; two or three clusters; batteries as drafts with missing values (so the publication checks show), published, with several versions, a status change, live values with seven days of history, an accident report, documents and a module list; an account for every role, the three LI roles included; tokens (read and read-write per cluster, and a global Full access). Every record it makes carries a demo mark, accounts, memberships, clusters and tokens included. Clearing never breaks real data: a demo record that real data uses stays, loses its mark and is listed in the result. The demo accounts' password comes from the `DEMO_USERS_PASSWORD` setting, never from code; without it, everything but the accounts is seeded and the card says so. Token values are shown once. Passports go through the normal publication, so their signatures verify. Planned as step 3d-3, before 3e. |
| 33 | A cleaner look (step 3e) | **The admin, cluster admin and help pages get decision 27's finish**, as in the approved mock-up `docs/mockups/dpp-v3-step3e-cleaner-look.html` | Each tab: an intro card with its one main button opening a window, rows that open in place with the risky actions last, rare settings in a small card at the end. **Help leaves the admin tabs** and stays in the top bar; it becomes one page that shows each reader only their parts (cluster admins get a new "Your cluster" part), and `/help/team` and `/admin/help` lead to the team's part. The tabs become "Clusters" and "API tokens", in the order of the work. **The Demo data card goes to the end of the Clusters tab.** **The two bulk token buttons stay**, under "More". **The API reference stays open to everyone**; its example battery ID comes only from a published demo battery, else none, never a real battery. **A cluster admin's token "delete" stays a switch-off**, now called "Deactivate token"; only the team deletes a token or switches it back on. **The demo data survives an app restart:** the seed's cluster tokens are the cluster's own (`autoClusterId`), so the app's start adds none, and Clear and Reset remove a demo cluster's own tokens with it without counting them as real use. Demo clusters that an earlier Clear or Reset after a restart already made real stay real (no automatic repair); the plan says how to tidy them by hand. Planned in `docs/superpowers/plans/2026-10-30-dpp-v3-step3e-cleaner-look.md`. |
| 34 | Purchaser editing and lifecycle (step 4) | **Four parts**, each ending with a working app: **4a** the cluster admin's battery page; **4b** the status change and repairs; **4c** successor passports, "invalid" and "marked for deletion"; **4d** hand-overs between clusters. **One mock-up** for all of step 4, approved by the product owner on 31 Oct 2026 with all eight screens as drawn: `docs/mockups/dpp-v3-step4-purchaser-and-lifecycle.html` | **4a:** cluster admins edit on their own page per battery, `/cluster-admin/batteries/{id}`, opened by "Manage" on their Registry rows and on the detail page, built from the team page's cards with no duplicates; only admin memberships give editing rights (an admin of one cluster and plain member of another edits only the first); the modules and versions are shown there read-only. **4b:** the status window asks "What happened?" first (Repaired / Prepared for re-use and placed on the market again / Remanufactured / Repurposed / Waste) and the app sets #22 from it; a repair entry is never changed or removed, a mistake gets a correcting entry; after remanufactured, repurposed or placed on the market again, the old passport takes no more status changes until its successor is linked. Settled for 4b on 1 Nov 2026: 4b offers "Repaired" and "Waste" only, and the other three choices come with 4c's linked passport; the team alone gets "Correct the values" in the same window (status kept, nothing added to the history, a new version, logged as a correction; it also fixes a waste battery's values); "Add a note to the history", for the team and the battery's cluster admins, adds an entry marked "Correction" without a new version; the demo data's DEMO-C7M-0001 gets the repair its accident report describes and a new DEMO-CORE-0003 is set to waste. Settled for 4c on 1 Nov 2026: 4c is two plans, 4c-1 the new linked passport and 4c-2 "invalid" and "marked for deletion"; Scania's new passport starts from the old battery (a new battery ID; the same serial number, batch and cluster; the service provider, manufacturing date, module list, re-stated values and last measured values with their times copied; its status as what happened; the warranty left for the team before publishing; the repair history and accident reports stay with the old passport); the team picks its operator, the old battery's pre-selected; the team alone cancels a new passport while the old one isn't inactive, which puts the old status back; an inactive passport takes no more changes, and feeds and uploads that find a battery by serial number pick the one that isn't inactive; another operator's details are saved without the new passport's ID or address, and linking needs it; the team can undo "invalid" and "marked for deletion", the reason staying in the audit log; the demo data gets DEMO-C13M-0001 repurposed with its published new passport, DEMO-CORE-0003 marked for deletion and one invalid battery whose reason only the team and market surveillance see. **4c:** the successor starts in the old battery's cluster (the team can change it); "invalid" freezes the passport (no new versions, status changes or live values) until the team undoes it, and its reason is seen only by the team and market surveillance while the public page shows "invalid" and the date; "marked for deletion" only for a waste battery, by the team, which can undo it. **4d:** while a hand-over waits the sending cluster keeps full access and the receiver sees nothing; the sender types the receiving cluster's ID and the app shows its name to confirm, so other customers' names stay hidden; the receiver accepts or declines on a "Waiting for you" card on its Registry, no e-mail; the team keeps its direct move (logged) and can cancel a waiting hand-over. Cluster API tokens stay live-values-only (J-10); status changes by upload come with step 5's upload. Each part adds its own demo example. |
